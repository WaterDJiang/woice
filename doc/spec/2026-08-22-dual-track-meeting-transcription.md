## 1. 问题确认与当前实现

当前基线和本轮实现边界是确定的：

- `SystemAudioCaptureService` 使用 ScreenCaptureKit 将电脑输出保存为同一 Recording ID 下的独立 48 kHz、双声道 CAF。
- 麦克风由 `RecordingService` 保存为 WAV，两条轨道均可在录音详情独立复听。
- 本轮已增加 `AudioTrackKind`、`MeetingTranscriptionMode`、来源字段和 meetingMix 文件契约，旧记录仍按麦克风来源兼容读取。
- 会议模式会在两条原轨提交后生成 16 kHz 单声道 WAV meetingMix 供统一回放；当前默认 `sourceSeparated` 为有效麦克风/系统音轨分别创建 Job，按音轨逐条进入本机或外部 ASR 确认队列并按时间线合并。
- `standardMix` 仅作为旧记录/显式兼容模式保留；它对 meetingMix 只转写一次，不再作为新设置默认值。
- 系统音频原始 CAF 发送外部 ASR 前会通过受控准备层转换为标准 WAV；原始 WAV/CAF 不覆盖、不删除。
- 仍待真实会议播放、长录音、系统轨失败和来源分离人工 Journey；外部 Provider 的真实双请求需在授权环境复验，这些不计入当前开发工作包退出条件。

因此，当前默认会议模式得到“两条原始音轨 + 分别转写后按时间线合并的一份原文”；来源只进入结构化时间戳/JSON，不插入纯文本原文。

## 2. 产品裁决

### 2.1 是否最后只保留一个音频文件

不应该只保留一个音频原件。

推荐的数据模型是：

```text
一场会议 Recording
├── 麦克风原始音轨.wav          不可变，代表本机用户/房间麦克风
├── 系统声音原始音轨.caf        不可变，代表电脑播放的会议/视频声音
├── 会议合成回放.wav            可删除并重建，负责统一回放
├── 默认会议原文                麦克风/系统轨分别转写后按时间线合并
└── 兼容标准原文（可选）      对 meetingMix 只转写一次
```

用户界面可以表现为“一场会议、一个主播放器、一份会议原文”，但存储层必须保留两条原始来源。原因：

- 合成后无法可靠还原哪一部分来自麦克风或电脑声音。
- 两轨同时说话时，先混音再转写通常比逐轨转写更容易漏句。
- 未来重转写、降噪、说话人分离和纠错都需要原始轨。
- 任一轨损坏或模型失败时，另一轨仍可独立使用。
- 原始素材来源与用户的隐私/外发授权需要可审计。

### 2.2 默认处理策略

- 默认为“完整会议（推荐）”：对齐两条有效原轨，生成 `meetingMix` 供回放，同时为麦克风与电脑声音分别创建 ASR Job，确定性合并结果。
- 只有一条原轨有效时，直接使用该轨的标准化输入，不生成无意义的双轨合成。
- 旧版“标准模式”单次混音转写只保留为历史兼容；它不能保证重叠说话完整，不再作为新设置默认值。
- 标准模式不承诺“我的麦克风/电脑声音”句级来源；需要来源标签时使用来源分离模式。
- 不根据 VAD 或回声指标静默自动切换为两次转写；模式、预计处理时间和外发文件数始终可见。
- 旧的单轨录音保持现有体验，不显示不必要的音轨概念。

## 3. 用户目标

- 开启会议录制后，录音结束能得到本机与远端双方的完整文字。
- 在历史中只看到一条会议素材，而不是两条互不关联的录音。
- 默认可以统一回放整场会议，也能展开查看两条原始音轨。
- 默认以约一倍会议时长完成一次转写；需要来源标签时可显式选择高精度来源分离。
- 任一音轨或转写失败时，明确知道已保存什么、缺少什么、如何重试。
- 使用外部 ASR 时，明确知道将发送一个合成文件还是两条原轨派生输入。

## 4. 术语与语义

### 4.1 音轨来源

新增值类型 `AudioTrackKind`，不是新的领域根对象：

- `microphone`：麦克风原始轨。
- `systemAudio`：ScreenCaptureKit 系统输出原始轨。
- `meetingMix`：由原始轨生成的派生回放轨。

UI 文案：

| 内部值 | 用户文案 | 不使用 |
|---|---|---|
| microphone | 我的麦克风 | Speaker 1、本地 Provider |
| systemAudio | 电脑声音 | Speaker 2、远端说话人 |
| meetingMix | 会议回放 | 主音轨、最终原件 |

“电脑声音”只描述采集来源，不等于某个具体参会人。多人会议中的远端参与者仍可能都在同一系统音轨中；说话人分离是后续独立能力。

### 4.2 有效音轨

音轨必须同时满足：

- 文件容器可读取。
- 时长大于 0.05 秒。
- buffer/frame 数大于 0。
- 峰值高于静音阈值，或经 VAD 判断存在有效语音。

会议 Recording 的可用性改为“至少一条原始音轨有效”，不能继续以麦克风是否有声作为整场录音的唯一成功条件。

## 5. 数据契约

### 5.1 RecordingRecord 兼容扩展

保留现有：

- `audioFileName` 继续表示麦克风原始 WAV。
- `systemAudioFileName` 继续表示系统声音原始 CAF。
- `transcript` 继续作为合并原文的兼容投影。
- `transcriptSegments` 继续作为结构化时间戳来源。

新增可选字段：

- `systemAudioDuration: TimeInterval?`
- `systemAudioStartOffset: TimeInterval?`
- `meetingMixFileName: String?`
- `meetingTranscriptionMode: MeetingTranscriptionMode?`

旧记录缺少这些字段时继续解码；`systemAudioStartOffset` 缺失时不得假定绝对同步，只能使用现有近似起点或要求重新生成合并结果。

### 5.2 TranscriptSegment 扩展

新增：

- `sourceTrack: AudioTrackKind?`

兼容规则：

- 旧 Segment 缺少来源时按 `microphone` 读取。
- 标准模式 Segment 来源为 `meetingMix`，不推断句级原轨。
- 来源分离模式必须写入 `microphone/systemAudio`，合并排序使用 `segment.start + track.startOffset`。
- 当某轨只有整段文本、没有时间戳时，保存为该轨的整段结果，但不与另一轨交错排序。

`transcriptSegments` 是会议原文的结构化真相；`transcript` 是为标题、复制、旧 RPC 和旧 UI 保留的可重建文本投影。

### 5.3 ProcessingTask 扩展

新增可选字段：

- `sourceTrack: AudioTrackKind?`
- `meetingTranscriptionMode: MeetingTranscriptionMode?`

`MeetingTranscriptionMode` 只有两个值：

- `standardMix`：历史/显式兼容模式，对 meetingMix 只转写一次。
- `sourceSeparated`：默认完整会议模式，两条有效原轨分别转写。

幂等键：

```text
{recordingID}:transcription:microphone
{recordingID}:transcription:systemAudio
{recordingID}:transcription:meetingMix
{recordingID}:meetingTranscriptMerge
{recordingID}:meetingMix
```

任务查询和状态更新必须使用 `kind + sourceTrack` 或完整幂等键，不能继续只按 `ProcessingTaskKind.transcription` 更新第一条任务。从标准模式切换到来源分离重转写时创建新 Transcript Artifact，不覆盖已有原文。

旧 ProcessingTask 缺少来源时按麦克风任务兼容。

## 6. 统一时间基准

当前麦克风先启动，系统音频后启动，两轨起点存在偏移。会议转写不能只把两个 ASR 结果都从 0 秒开始排序。

### 6.1 采集要求

- 用户发起录音时创建一次单调时钟 Session Anchor。
- 麦克风写入首帧时记录相对 Anchor 的偏移。
- 系统音频首个 CMSampleBuffer 使用 Presentation Timestamp/主机时间映射到同一 Anchor。
- 停止时持久化每轨开始偏移、有效时长、帧数、采样率和声道数。
- 时钟元数据不修改原音频容器，只作为 Recording 的轨道元数据。

### 6.2 对齐规则

- 合并时间 = 轨内时间 + 轨道开始偏移。
- 两轨时长不一致时不裁掉较长轨；统一回放对缺失区间补静音。
- 偏移未知时不生成声称精确对齐的 meetingMix；用户可分轨复听或选择来源分离转写，UI 不伪造统一时间线。
- 不使用 LLM 猜测时间顺序。

## 7. 音频标准化

系统轨是 48 kHz 双声道 CAF，当前 ASR 契约按 WAV 发送，必须增加受控的输入准备层。

### 7.1 AudioPreparationService

职责：

- 接收已提交的原始 WAV/CAF 和目标 Provider 输入配置。
- 按共享 Session 时钟对齐有效原轨，生成固定增益、预留头间且防削波的可重建 `meetingMix.wav`。
- 通过 AVFoundation/AVAudioConverter 生成标准 ASR 临时 WAV。
- 默认输出 PCM 16-bit、单声道、16 kHz；Provider 明确需要其他格式时由能力声明覆盖。
- 保留轨内时长映射，转换前后时长偏差不得超过 50 ms 或 0.5%。
- 临时文件位于受控工作目录，任务完成或失败后清理。
- 不覆盖、不改名、不重新编码原始 WAV/CAF。

非职责：

- 不做自动说话人识别。
- 不用 LLM 清理重复内容。
- 不修改 Provider 路由或外发授权。
- 不自动做回声消除、内容去重或说话人判断；发现高重叠/回声风险可提示来源分离，但不静默切换模式。

### 7.2 MIME 与文件名

- 外部请求使用实际生成的 `.wav` 文件和 `audio/wav` MIME。
- 禁止把 `.caf` 内容伪装为 WAV 上传。
- 请求和日志不包含完整音频内容、转录文本或 API Key。

## 8. 处理流程

### 8.1 停止录音

```text
停止录音
  -> 分别提交麦克风 WAV 与系统 CAF
  -> 校验每轨容器、时长、帧数和信号
  -> 至少一轨有效即可创建 Recording
  -> 默认完整会议：生成 meetingMix 回放 -> 为每条有效原轨创建 ASR Job -> 时间线合并
  -> 兼容标准模式：生成 meetingMix -> 创建一条 ASR Job -> 发布会议原文
  -> 发布统一回放、原文版本和模式状态
```

### 8.2 本机 ASR

- 默认完整会议模式对麦克风、系统声音两条有效轨依次处理，首版保持串行，避免 WhisperKit/系统 Speech 资源争用。
- 兼容标准模式对 meetingMix 只执行一次本机推理，转写计算时长约等于会议时长，不生成原轨来源标签。
- 两种模式都保存 Provider/模型/模式快照；来源分离还分别保存原轨任务状态和错误。
- 录音期间的 VAD 后台分段继续只处理麦克风；系统轨首版在停止并提交 CAF 后处理。
- 麦克风已有的分段转写不能与 meetingMix 结果拼接冒充标准会议原文；来源分离模式可复用完整的麦克风分段结果。
- 系统轨无可听信号时标记 `noSpeech`，不是 Provider 失败。

### 8.3 外部 ASR

- 标准模式显示目标域名、“会议合成音频”和一次预计请求；用户确认后只上传 meetingMix 的标准化临时 WAV。
- 来源分离模式显示目标域名、两种数据类型、两条音轨和两次预计请求；一轨成功不自动重试另一轨。
- 用户拒绝后两条原始轨继续保存在本机，任务保持可解释的等待/取消状态。
- 不把过去对“麦克风 WAV”的授权扩展成 meetingMix 或系统音轨授权。
- Provider 不支持时间戳时，标准模式仍可保留一份完整原文；来源分离模式保留两份分区原文。

### 8.4 来源分离模式的确定性原文合并

`MeetingTranscriptMerger` 只在来源分离模式使用，只做：

- 将每个 Segment 转换到 Session 时间轴。
- 按开始时间、结束时间、稳定音轨顺序排序。
- 保留 `sourceTrack`。
- 生成结构化 Segment 列表和兼容纯文本投影。

纯文本原文只保留内容，不插入来源标签：

```text
我们先确认今天的目标。
好的，先讨论发布时间。
```

来源只保存在 `TranscriptSegment.sourceTrack`、时间戳片段 UI 和 JSON 导出中。

不做：

- 根据文字内容删除疑似重复句。
- 把“电脑声音”推断成具体人名。
- 用 LLM 改写、总结或重排原始转写。

两轨重叠讲话时，两条 Segment 都保留，并在 UI 中按来源并列或相邻展示。标准模式直接使用 meetingMix 的 ASR 结果，不调用本合并器。

## 9. 统一回放与派生音频

### 9.1 用户体验

会议详情默认展示：

```text
会议回放
[播放] [暂停] [拖动]  32:18

原始音轨 ▸
  我的麦克风.wav
  电脑声音.caf
```

用户看到的是一个 Recording，不需要在历史列表管理两条记录。

### 9.2 meetingMix

- `meetingMix.wav` 是派生 Artifact，不是原件。
- 默认完整会议模式在两条原轨已安全提交后生成 meetingMix 作为统一回放输入，同时分别提交两条原轨转写任务；生成过程不得阻止 Recording 进入“音频已保存”状态。`standardMix` 仅在兼容模式下把 meetingMix 作为 ASR 输入。
- 只有一轨有效或未启用转写时，统一回放/导出可继续按需生成或直接使用有效原轨。
- 使用统一时间基准补齐起始/结束静音。
- 两轨混合前做固定增益和防削波；规则确定且有测试，不交给 LLM。
- 删除缓存不影响 Recording；下次播放或标准模式重转写时可从原始双轨重建。
- 永久删除会议时，原始轨和派生轨按同一可恢复删除策略处理。

如果统一回放服务能直接同步调度两条原始轨，可不生成缓存；但导出“会议合成音频”仍生成明确的派生文件。实现方案必须通过偏移、拖动、暂停恢复和长录音同步测试后再冻结。

## 10. UI/UX

### 10.1 录音中

- 同时显示“麦克风”和“电脑声音”状态、输入信号和失败说明。
- 电脑声音启动成功但无 signal 时显示“等待电脑声音”，不显示“已录到”。
- 任一轨失败时说明另一轨是否继续。

### 10.2 停止后处理

- 标准模式按阶段显示：`正在保存两条音轨 -> 正在生成会议回放 -> 正在转写会议`，不显示 1/2。
- 来源分离模式显示：`正在转写我的麦克风 1/2 -> 正在转写电脑声音 2/2 -> 正在整理来源原文`。
- 只有一条有效轨时显示 `正在转写电脑声音` 或 `正在转写麦克风`，不显示 1/2。
- 来源分离模式一轨失败时显示部分完成，例如“麦克风已转写；电脑声音转写失败，可重试”。

### 10.3 录音详情

- 会议详情只显示一个主“会议回放”。
- “原始音轨”DisclosureGroup 中保留两轨独立复听、文件状态、时长和来源。
- 转写模式使用原生 Picker：`完整会议（推荐，分别转写后合并）` / `快速混音（兼容，转写一次）`，并说明只影响新转写/重转写。
- 标准原文不显示伪造的原轨 Badge 或来源筛选。
- “原文”区域只显示合并后的说话内容，不插入“我的麦克风/电脑声音”文字 Badge。
- 声音来源只在时间戳片段的辅助元数据、来源筛选和 JSON `sourceTrack` 中展示；复制原文不携带来源标签。
- 没有精确时间戳时改为两个来源区块，不显示伪时间。

### 10.4 历史与导出

- 历史列表仍是一条会议记录，显示“双音轨”与转写完成度。
- 导出选项：会议合成音频、两条原始音轨、完整会议原文、时间戳 JSON、Markdown；只有已生成来源分离版本时才提供分轨原文。
- 默认 Markdown 包含转写模式、模型快照和时间戳；来源分离版本额外包含原轨来源。不包含 API Key、内部路径或错误堆栈。

## 11. 失败语义

| 场景 | 状态 | 用户结果 |
|---|---|---|
| 麦克风有效、系统轨无声 | 单轨可用 | 保存并转写麦克风；提示未检测到电脑声音 |
| 麦克风无声、系统轨有效 | 单轨可用 | 保存并转写电脑声音；不把整场录音标记失败 |
| 两轨均有效，完整会议（默认） | 双轨可用 | 分别转写并合并，保留结构化原轨来源 |
| 两轨均有效，快速混音（兼容） | 双轨可用 | 生成 meetingMix 并只转写一次 |
| 来源分离的一轨 ASR 失败 | 部分完成 | 保留成功原文和两条原始轨，允许只重试失败轨 |
| meetingMix ASR 失败 | 音频已保存 | 会议回放和两条原轨安全，可重试或显式改用来源分离 |
| 系统 CAF 无法标准化/混合 | 合成输入失败 | 两条原轨保留，不静默改为只转写麦克风 |
| Provider 无时间戳 | 标准原文或分轨完成 | 标准模式保留一份完整原文；来源分离显示两个来源区块 |
| 外部标准模式待发送 | 等待确认 | 显示域名、一个会议合成文件和一次请求 |
| 外部来源分离待发送 | 等待确认 | 显示域名、两条音轨和两次请求 |
| meetingMix 生成失败 | 回放/转写派生失败 | 两条原始轨仍可分别播放，标准模式不启动 ASR |

## 12. 隐私与安全

- meetingMix 依然包含麦克风与系统音频两类原始数据；外发确认必须说明“会议合成音频”包含两种来源。
- 本机 Provider 失败不自动切换外部 Provider。
- API Key 继续只进 Keychain，不写入任务、Transcript、Manifest、日志或临时目录。
- 临时标准化 WAV 使用独立工作目录、随机文件名和任务结束清理。
- 日志只记录文件类型、字节、时长、轨道类型、Provider/模型 ID 和稳定错误码，不记录音频或完整原文。
- 原始 WAV/CAF 创建后不可原位修改；重转写和合并只创建新的派生结果。

## 13. 兼容与迁移

- 旧 Recording 没有系统音轨：保持单轨行为。
- 旧 Recording 有 CAF、但系统轨未转写：详情显示“电脑声音尚未转写”，用户可显式发起“补转写电脑声音”。
- 不在升级后自动批量转写历史 CAF，避免无提示占用资源或外发。
- 旧 Segment 没有 `sourceTrack`：按麦克风处理。
- 旧 ProcessingTask 没有 `sourceTrack`：按麦克风任务处理。
- Schema/JSON/SQLite payload 变更必须带解码兼容和迁移契约测试。

## 15. 验收标准

- AC-DT-001：会议模式录制有效麦克风与系统声音后，Recording 同时引用两条可读取原始轨。
- AC-DT-002：任一轨无声或失败时，另一条有效轨仍保存并进入对应转写。
- AC-DT-003：标准模式对两条有效原轨只生成一条 `transcription:meetingMix` Job，ASR 只接收一个真实 WAV 输入。
- AC-DT-004：来源分离模式的两条 ASR Job 有不同幂等键、同一模型快照和独立状态；不会把 CAF 伪装为 WAV。
- AC-DT-005：来源分离且两轨有时间戳时，合并 Segment 按统一 Session 时间排序并保留来源。
- AC-DT-006：Provider 无时间戳时，标准模式保留完整原文；来源分离显示分轨原文，不伪造交错顺序。
- AC-DT-007：切换模型只重转写用户选择的轨或整场会议，原始 WAV/CAF SHA-256 不变。
- AC-DT-008：外部 ASR 发送前显示目标域名、内含的原始数据类型、实际文件数和请求数；标准模式为 1，来源分离为 2，取消后为 0。
- AC-DT-009：会议详情默认一条统一回放，原始音轨可展开并分别播放。
- AC-DT-010：meetingMix 删除后可由原始双轨重建；派生失败不影响原音频，但标准模式 ASR 必须等待重建成功或用户显式改用来源分离。
- AC-DT-011：历史中一场会议只显示一条 Recording，且能看出双轨/部分转写状态。
- AC-DT-012：标准原文导出明确标注“合成会议音频”；来源分离原文和时间戳 JSON 保留原轨来源；均不含 API Key 和内部绝对路径。
- AC-DT-013：旧单轨 Recording、旧双轨未转写记录和旧 ProcessingTask 均可读取。
- AC-DT-014：真实 Mac 分别完成“标准模式 -> meetingMix -> 单次转写”和“来源分离 -> 两轨转写 -> 合并原文”两条 Journey。
- AC-DT-015：`make test`、`make docs-check`、`make harness-check`、`make verify` 和新增的真实会议门禁全部通过后，状态才可改为已实现。

## 16. 测试矩阵

### Domain/Storage

- 新旧 Segment/Task/Recording 编解码。
- `sourceTrack` 缺失的兼容默认。
- meetingMix 单 Job 与来源分离双 Job 的幂等键、Lease、恢复与重试。
- 原始文件哈希不变、派生文件可重建。

### Audio

- 48 kHz stereo CAF -> 标准 WAV。
- 麦克风不同采样率/声道 -> 标准 WAV。
- 双轨对齐、固定增益、防削波和 meetingMix 重建的确定性。
- 起点偏移、补静音、长短轨、拖动和暂停恢复。
- 静音、削波、空容器、损坏 CAF、磁盘不足。

### ASR/Merge

- 麦克风固定说“本地发言”，系统轨固定说“远端发言”：默认完整会议分别转写并合并，兼容快速混音才由一次 ASR 处理 meetingMix。
- 顺序发言、重叠发言、同内容回声、只有一轨有声。
- 有时间戳与无时间戳 Provider。
- meetingMix 失败重试、来源分离一轨成功一轨失败、App 中断后只恢复未完成任务。

### Privacy/UI

- 本机标准/来源分离转写均为零外部请求。
- 外部确认文案与实际请求数量一致。
- 状态同时有图标、文字和轨道名。
- 键盘、VoiceOver、深色、高对比和 Reduce Motion 真实检查。

## 17. 明确后置

- 远端多人说话人分离与姓名识别。
- 回声消除、跨轨自动去重和会议应用级来源识别。
- 录音中的系统轨实时增量转写。
- 自动摘要、待办和 Agent 处理。
- 云端多人会议专用 API 或 Provider 私有多通道协议。

这些能力不得阻塞双轨原件安全、默认分别转写合并和兼容 meetingMix 单次 ASR 的首个闭环。
